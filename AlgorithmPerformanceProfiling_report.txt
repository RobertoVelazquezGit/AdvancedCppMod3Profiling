Algorithm Performance Profiling Report
=======================================

1. Objective
------------
This report analyzes the gprof output generated by the AlgorithmProfiler
benchmark. The benchmark compares sorting algorithms, search algorithms, hash
lookups, and sequential versus random memory access patterns for data sets of
1,000, 10,000, and 100,000 integers.

The executable was built with gprof instrumentation and the report was
created with:

    gprof ./build/Mod3ProfilingPerformance gmon.out > StatisticalBenchmarking.txt

2. Overall Result
-----------------
The profiled program accumulated approximately 0.81 seconds of execution
time. The gprof report uses statistical sampling:

    Each sample counts as 0.01 seconds.

Consequently, very short functions can appear with 0.00 seconds even though
they were executed and did consume time.

3. Main Results
---------------

                                  300        0.00 s          0.07 s

AlgorithmProfiler::buildHashIndex   3        0.00 s          0.02 s

AlgorithmProfiler::binarySearch  3,000       0.00 s          0.00 s
AlgorithmProfiler::hashLookup    3,000       0.00 s          0.00 s

Self time is the time spent directly inside a function. Total time includes
the time spent in functions called by that function.

4. Interpretation
-----------------

4.1 Linear search

linearSearch is the function with the highest self time:

    0.11 seconds, 3,000 calls, 13.58 percent of the sampled time.

This result is consistent with its O(n) complexity. The benchmark searches
for the last element of each data set using data.back() as the target. The
algorithm therefore normally examines most of the vector before finding the
value.

The report also shows many calls to vector::size() and vector::operator[].
These calls are not necessarily expensive individually. They appear because
they are executed repeatedly inside the search and loop operations.

4.2 Bubble sort

bubbleSort was called twice, for the 1,000- and 10,000-element data sets. It
was deliberately not run for 100,000 elements because its O(n^2) complexity
would require an impractical number of comparisons.

The function shows approximately:

    0.02 seconds of self time
    0.14 seconds of total time
    19.4 percent of the sampled time

The total time includes comparisons, vector accesses, swaps, and iterator
operations used internally by the implementation.

4.3 Optimized sort

optimizedSort uses std::sort and was called once for each data size. Its own
time appears as 0.00 seconds because the function is very short compared with
the 0.01-second sampling resolution. The call graph reports approximately
0.03 seconds of total time.

This does not mean that std::sort takes zero time. It means that gprof did not
collect enough samples to assign measurable self time directly to this
function.

4.4 Binary search

binarySearch was called 3,000 times and appears with 0.00 seconds. This is
expected for an O(log n) algorithm operating on sorted vectors. The number of
comparisons grows slowly as the data size increases, so its execution time is
very small compared with linear search and sorting.

4.5 Hash lookup

hashLookup was also called 3,000 times and appears with 0.00 seconds. This is
consistent with the expected average O(1) lookup complexity of
std::unordered_map. The construction of the hash index is more visible than
individual lookups because building the index processes every input element.

4.6 Sequential versus random memory access

processDataSequential has approximately 0.07 seconds of total time, whereas
processDataRandom has approximately 0.27 seconds of total time.

Sequential access benefits from contiguous memory and CPU cache locality.
Random access is less cache-friendly and can cause more cache misses.

The random benchmark does not measure memory access alone. It also creates,
initializes, and shuffles an index vector on every call:

    std::iota(...)
    std::shuffle(...)
    std::mt19937

The gprof report shows that std::shuffle and the Mersenne Twister generator
also consume a significant amount of time. Therefore, the 0.27-second total
should be interpreted as the cost of random index generation plus random data
access.

5. Complexity Conclusions
------------------------
The benchmark supports the expected complexity differences:

- bubbleSort has O(n^2) complexity and becomes expensive rapidly.
- std::sort has approximately O(n log n) complexity and scales much better.
- linearSearch has O(n) complexity.
- binarySearch has O(log n) complexity, provided the data is sorted.
- hashLookup has average-case O(1) complexity after the hash index is built.
- Sequential memory traversal is generally more cache-friendly than random traversal.

6. Limitations
--------------
The benchmark uses gprof's statistical sampling rather than measuring every
individual operation. Since each sample represents approximately 0.01 seconds,
short functions such as binarySearch, hashLookup, and optimizedSort may appear
with zero self time.

The benchmark is also affected by:

- Random data generation.
- Vector copies made before sorting.
- Hash-map construction and memory allocation.
- Index creation and shuffling in processDataRandom.
- Operating-system scheduling and CPU frequency changes.

The measured values should therefore be used to compare broad performance
trends, not as exact nanosecond-level timings.

7. Recommendations
------------------
For more precise measurements of short operations, use std::chrono and repeat
each operation many more times. To isolate cache behavior, create and shuffle
the random index vector once, outside the timed processing loop, and reuse it
for both measurements.

For a cleaner gprof profile, consider running separate benchmark executables
or separate program modes for sorting, searching, hashing, and memory access.
This prevents unrelated setup and STL operations from dominating the same
profile.
