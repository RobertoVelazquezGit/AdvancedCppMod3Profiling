Memory Cache Analysis Report
============================

1. Objective
------------
This report analyzes the gprof profile generated by MemCacheAnalysis.cpp.
The benchmark compares:

- Row-major and column-major matrix traversal.
- Array of Structures (AoS) and Structure of Arrays (SoA) particle layouts.
- The effect of memory layout and access patterns on execution time.

The benchmark validates that both implementations produce identical numerical
results before repeating the calculations for profiling.

2. Profiling Configuration
--------------------------
The program was built with gprof instrumentation and executed before creating
the report. The gprof output states:

    Each sample counts as 0.01 seconds.

The flat profile contains approximately 0.50 seconds of sampled execution
time. Because gprof uses statistical sampling, short functions can show
0.00 seconds even when they were executed.

The main benchmark uses three matrix sizes and three particle counts. The
reported 303 calls for the main processing functions correspond to the three
validation calls plus the repeated benchmark calls.

4. Meaning of the Columns
--------------------------
Self time is the time spent directly inside the function itself. It excludes
time spent in functions called by that function.

Total time includes the function's self time and the time propagated from its
children in the call graph.

Cumulative seconds is the running total of the self times of the functions
listed above the current row in the flat profile. It is not the exclusive time
of the current function.

The self and total ms/call columns are averages per call. For example, the
SoA calculation has 0.12 seconds of self time over 303 calls:

    0.12 seconds / 303 = approximately 0.40 milliseconds per call.

5. Particle Layout Results
--------------------------

5.1 Array of Structures

ParticleSystemAoS::calculateKineticEnergy() shows:

    303 calls
    0.06 seconds of self time
    0.07 seconds of total time
    12 percent of the flat-profile sampled time

The function traverses a contiguous vector of Particle objects. Each Particle
contains position, velocity, mass, and ID fields. The calculation only needs
the velocity and mass fields, so some data belonging to each loaded structure
is not required for this operation.

5.2 Structure of Arrays

ParticleSystemSoA::calculateKineticEnergy() shows:

    303 calls
    0.12 seconds of self time
    0.15 seconds of total time
    24 percent of the flat-profile sampled time

The SoA calculation reads the velocity and mass arrays sequentially. This
layout can improve locality when an operation processes only selected
attributes. However, this particular profile shows SoA taking more self time
than AoS.

This result does not contradict the general cache argument. Performance also
depends on the number of memory streams, compiler code generation, CPU cache
state, vector implementation details, and measurement noise. With this
benchmark, SoA is not automatically faster; the measured result must be
interpreted for this workload and platform.

The call graph shows that the SoA method directly accounts for approximately
0.12 seconds and receives approximately 0.03 seconds from vector operations.
The AoS method accounts for approximately 0.06 seconds directly and receives
approximately 0.01 seconds from iterator operations.

6. Matrix Traversal Results
---------------------------

6.1 Row-major traversal

matrixSumRowMajor() shows:

    303 calls
    0.03 seconds of self time
    0.07 seconds of total time
    6 percent of the flat-profile sampled time

The function accesses each row from left to right. Elements within a row are
stored contiguously, so this access pattern generally benefits from spatial
cache locality.

6.2 Column-major traversal

matrixSumColumnMajor() shows:

    303 calls
    0.04 seconds of self time
    0.09 seconds of total time
    8 percent of the flat-profile sampled time

The column-major version is slightly more expensive in this profile. The
matrix type is std::vector<std::vector<int>>, so every row is a separate
allocation. Moving down a column jumps between separate row allocations rather
than reading contiguous integer elements.

The column-major implementation also performs a bounds check for each possible
row and column pair because the nested vectors may have different lengths.
For a rectangular matrix this check is unnecessary but it makes the function
safe for irregular matrices.

The profile therefore supports the expected conclusion that row-major access
is more cache-friendly for this representation, while column-major traversal
has less favorable locality and additional loop overhead.

7. Random Initialization Cost
-----------------------------
The random distribution function appears with approximately:

    2,240,000 calls
    0.06 seconds of self time
    0.10 seconds of total time
    12 percent of the flat-profile sampled time

This cost comes from initializing the AoS and SoA systems. It is not part of
the kinetic-energy calculation itself. The fixed random seed ensures that both
particle systems receive the same values, which is necessary for a fair
numerical comparison.

8. Validation
-------------
The benchmark compares the row-major and column-major matrix sums and checks
that they are identical. It also compares the AoS and SoA kinetic-energy
results. Matching results confirm that the two implementations perform the
same logical calculations before their performance is compared.

9. Main Conclusions
-------------------

- Row-major matrix traversal is faster in this profile than column-major
  traversal for the vector-of-vectors representation.
- Column-major traversal has poorer locality because consecutive accesses move
  between separately allocated rows.
- The SoA kinetic-energy calculation consumes more sampled self time than the
  AoS version in this particular run.
- SoA can still be advantageous when processing only selected attributes, but
  its benefit must be measured for the actual workload.
- Random initialization is a significant part of the complete program profile
  and should be separated from processing measurements when necessary.
- The vector subscript operations appear frequently because the benchmark
  performs tens or hundreds of millions of element accesses. Their high call
  counts do not mean that each individual subscript is expensive.

10. Limitations and Improvements
--------------------------------
The profile is based on 0.01-second samples, so short operations may be
reported as 0.00 seconds. The results can also be affected by CPU scheduling,
cache warming, compiler options, and the current machine load.

For a cleaner cache comparison:

- Generate the matrix and particles outside the timed processing region.
- Reuse the same initialized data for every measurement.
- Run each traversal many more times.
- Measure with std::chrono for short functions.
- Use a contiguous one-dimensional matrix representation if the goal is to
  compare true row-major and column-major traversal without separate row
  allocations.
- Use hardware counters such as cache references and cache misses when
  available.

The current results are useful for identifying broad trends, but they should
not be treated as exact hardware-level cache-miss measurements.
